# gramkit-ts vs Python gramkit on Conduit, 2026-11-08

One session, one box, back to back. Rig and procedure as Python gramkit's README Performance section (its 2026-11-06 run):
Arjay McCandless's multicore-server-challenge Conduit (19 endpoints, 197-check conformance, full seed), its Go load
generator from a second box in the same datacenter, `switch.sh <name> --no-conformance` (fresh DB, Postgres restart,
page cache dropped) then `conduit-loadgen search` with default flags (warm-up 500, doubling probes, bisect to 5%,
5-minute holds stepping down 5%). Score = most users held 5 minutes with p95 < 500 ms, p99 < 1 s, < 1% errors.
The method is packaged as a Claude Code skill: [howmanyusers](https://github.com/tonysafonov/howmanyusers).

- **Target:** Synteq, 2 dedicated vCPU (Xeon Platinum 8260) / 4 GB, Ubuntu 24.04. Postgres 18 and nginx on the same box.
- **Every app:** 2 workers (one per core), 10 DB connections per worker, nginx in front, keep-alive 95 s, rate limiter
  off, one access-log line per request.
- **Python gramkit:** `bench/conduit-python/` on gramkit core as of 2026-11-07, CPython 3.14.8, uvicorn,
  SQLAlchemy 2 + asyncpg, tuning `workers2-pool10.env`.
- **gramkit-ts:** `bench/conduit/` on the same framework code as the app, Hono + Drizzle + postgres.js, Node 26.12.1
  (esbuild bundle) and Bun 1.4.4 (source). "prepared" = the one change in `bench/conduit/overlays/prepared/`: hot repo
  queries use Drizzle's `.prepare()`.
- **Reference:** the challenge's plain `examples/python` (FastAPI + asyncpg, no ORM, no middleware), to read the
  box's drift.

All six pass conformance 196/197 (the known `offset=100000000` timeout on 2 cores). 0 errors in every scored hold.

## Reading it

- **gramkit-ts holds 2.25× (Node) and 2.33× (Bun) what Python gramkit holds** as a normal Drizzle app, and 2.75× /
  3.1× with prepared statements.
- **The app is 2.7–3.7× cheaper per request** (3.94 ms → 1.07–1.48 ms). Users grow less than that because Postgres and
  nginx on the same 2 cores cost the same per request whatever the app is; at the TS scores the box is at 99–100% CPU.
- **Drizzle's default is the biggest single knob.** Query-builder queries go out unprepared, so Postgres plans each one:
  1.09–1.16 ms of Postgres CPU per request against 0.67–0.69 ms prepared, which is what asyncpg (Python) already gets
  by default. `.prepare()` on hot queries gave +22% (Node) and +32% (Bun). Worth making the default pattern in gramkit-ts.
- **Node vs Bun** is within one search step (5%) as a normal app, because Postgres dominates; prepared, Bun leads by 12%
  (app 1.07 vs 1.36 ms per request). Bun idles at less than half Node's memory (155 vs 346 MB for 2 workers + supervisor).
- **Against the bare reference:** a full gramkit-ts app ties plain FastAPI-with-no-ORM (2,700–2,800 vs 2,700), and beats
  it once prepared. Python gramkit holds 44% of it, the same share as on 11-01 (41%) and 11-06 (42–43%).
- **Box drift:** the reference held 2,700 tonight vs 3,000–3,100 on 11-06 and 3,400 on 11-01. Python gramkit held 1,200
  vs 1,300 on 11-06 (its first hold at 1,300 missed p99 by 1.5 s). Only same-night ratios are fair.

## Caveats

- One search per setup; the search resolves 5%, and run-to-run noise is about one step.
- Python gramkit was not given further tuning tonight (Granian, SQLAlchemy Core on hot paths): it's the shipped template
  with a worker per core, as before. The prepared overlay has no Python counterpart because asyncpg already prepares.
- The TS bench declares its differences from the Python one in `bench/conduit/README.md`: responses not re-validated
  at runtime (Pydantic does), no `pool_pre_ping`, no overflow, pino's async writes vs Python's log-listener thread,
  BEGIN opened before the handler.
- Conduit measures the framework's layers with JWT auth; it does not exercise Telegram auth, sessions or payments.
